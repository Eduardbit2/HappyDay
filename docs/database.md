# SQLite и доменная модель

База находится в `APP_DATA_DIR/happyday.db`, резервные копии — в
`APP_DATA_DIR/backups`. По умолчанию это локальная папка `data`.
SQLite использует WAL, внешние ключи и ожидание блокировки до 5 секунд.
Приложение работает одним процессом; миграции выполняются до начала приема HTTP.

## Таблицы и правила

| Таблица | Назначение |
| --- | --- |
| `users` | Имя, уникальный логин, хеш пароля, роль admin/member, активность |
| `groups` | Название, иконка, цвет, порядок и признак системной группы |
| `birthdays` | Имя, день/месяц, необязательный год, одна группа, заметка, активность |
| `telegram_links` | Не более одного Telegram ID на пользователя; Telegram ID уникален |
| `deliveries` | Событие, получатель, интервал 7/1/0, статус, счетчик попыток и retry |
| `delivery_attempts` | Результат каждой попытки: номер, время, исход и ошибка |

Отсутствие строки в `telegram_links` означает отсутствие привязки и не запрещает
пользователю работать в web. Создание аккаунтов, Argon2 и авторизация описаны в [Авторизация](authentication.md).
Безопасная выдача Telegram-привязок будет добавлена вместе с ботом. Напрямую
создавать рабочие аккаунты SQL-командами не нужно.

Правила напоминаний пока являются фиксированными интервалами 7/1/0, отдельной
редактируемой таблицы правил нет. Год события содержится в `occurrence_date`.
Уникальный ключ доставки: именинник + дата наступления + интервал + пользователь.
Он исключает дубли записей задания. Гарантии отправки в Telegram и обработка
сбоя между отправкой и записью результата относятся к notification engine.
Даты и время журналов хранятся в UTC без смещения; в интерфейсе потребуется
явное преобразование в Europe/Moscow.

Системная группа имеет ID 1 и название «Без группы». Миграция создает ее один раз;
CHECK и триггеры запрещают удаление и изменение ее идентичности.
Иконка, цвет и порядок могут меняться. Удаление обычной группы допускается только
с выбором другой группы для переноса всех записей, включая архивные.

SQLite проверяет реальные календарные даты, в том числе столетние високосные
годы, и запрещает будущий год вставкой/обновлением через триггеры.
Год рождения неизвестен — хранится NULL. Для 29 февраля наступление события
в невисокосный год рассчитывается на 28 февраля. Возраст без года не выводится.

`app/birthdays/service.py` содержит общие операции создания, архивирования,
переноса групп и календарные функции для будущих web/bot.
Дубль имени и полной даты требует `confirm_duplicate=True`.
Сравнение имен использует Unicode NFC, нормализацию пробелов и casefold;
проверка учитывает и архивные записи. Это предупреждение приложения, а не
уникальное ограничение БД: подтвержденные дубли допустимы.
Сервисы выполняют flush, но не commit: вызывающий код управляет транзакцией
через `with Session(engine) as session, session.begin(): ...`.

## Миграции и проверка

При запуске FastAPI автоматически выполняется upgrade до актуальной revision.
Повторный запуск не создает группы или резервные копии заново, если revision
уже актуальна. Ошибка backup или миграции прерывает запуск.
Для существующей базы backup создается до изменения схемы.

```powershell
.\.venv\Scripts\python.exe -m app.db upgrade
.\.venv\Scripts\python.exe -m app.db check
.\.venv\Scripts\python.exe -m app.db backup
```

`check` проверяет текущую revision и расхождения моделей/миграций через Alembic.
Триггеры и бизнес-ограничения дополнительно проверяются интеграционными тестами.
`/health/ready` проверяет доступность БД и актуальность revision; при ошибке
возвращает 503 без внутренних деталей. Telegram пока не проверяется.

Начальная миграция `0001_domain` содержит зафиксированную схему и не импортирует
текущие модели. При следующих изменениях добавляем новую revision с
`down_revision = "0002_auth"`, существующую опубликованную миграцию не меняем.
Для миграций используется управляемое соединение в `app/db/migrations.py`;
прямой запуск стандартного Alembic CLI без него запрещен, чтобы не обходить backup.

## Backup, восстановление и откат

Backup использует SQLite Online Backup API, учитывает подтвержденные записи WAL
и проверяется через `PRAGMA integrity_check`.
Копировать только активный файл БД при работающем приложении недостаточно.
Готовая копия получает расширение `.db` только после успешной проверки;
незавершенные файлы `.partial` не предназначены для восстановления.

Для восстановления остановите приложение, сохраните текущий каталог данных
и разверните выбранную копию как `happyday.db` в отдельном пустом каталоге.
Укажите этот каталог в `APP_DATA_DIR`. Не подкладывайте старый backup рядом
с WAL/SHM от другой базы. Запустите `check` с соответствующей копии версией кода,
затем приложение. Восстановление на текущей версии кода при необходимости
выполнит новые миграции; для отката выберите код версии резервной копии.

Начальный `downgrade` удаляет все доменные таблицы и данные. Он предназначен
для тестов на одноразовой базе; production-откат выполняется восстановлением
backup и соответствующей версии кода. Пользовательская CLI поэтому не
предоставляет команду downgrade.

Миграции выполняются до старта сервера и могут блокировать запись. Не запускайте
CLI upgrade параллельно работающему приложению. Перед большими будущими
изменениями схемы потребуется остановка приложения. Автоматическая очистка
старых backup и процедура Synology/Hyper Backup относятся к этапу развертывания.
